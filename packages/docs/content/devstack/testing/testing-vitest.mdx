Use the `vitest` subpath for node-mode unit and integration tests.

```ts title="vitest.config.ts"
import { defineConfig } from 'vitest/config';
import { devstackVitePlugin } from '@mysten-incubation/devstack/vite';
import {
	devstackVitestServerConfig,
	devstackVitestTestConfig,
} from '@mysten-incubation/devstack/vitest';

export default defineConfig({
	plugins: [devstackVitePlugin()],
	server: devstackVitestServerConfig(),
	test: devstackVitestTestConfig({
		threads: 'single',
		testSetup: { requireDevstack: true },
	}),
});
```

Vitest runs its own Vite pipeline, so `devstackVitePlugin()` is added here too — otherwise the
`@generated` alias would not resolve when importing generated code under test.

Current exports from `@mysten-incubation/devstack/vitest` include:

- `devstackVitestTestConfig`
- `devstackVitestServerConfig`
- `useDevstackTestSetup`
- `runDevstackBeforeAll`
- `runDevstackAfterAll`
- `getStackContext`
- `loadStackContext`
- `resolveVitestEnv`

Programmatic setup is useful when you own a shared setup file:

```ts title="test/setup.ts"
import { afterAll, beforeAll } from 'vitest';
import { useDevstackTestSetup } from '@mysten-incubation/devstack/vitest';

useDevstackTestSetup({ beforeAll, afterAll }, { requireDevstack: true });
```

Inside a test, read the captured manifest context:

```ts
import { expect, test } from 'vitest';
import { getStackContext } from '@mysten-incubation/devstack/vitest';

test('has a wallet endpoint', () => {
	const ctx = getStackContext();
	expect(ctx?.endpoint('wallet-app')).toMatch(/^http/);
});
```

The helpers do not boot a supervisor by themselves. Start one with `devstack up`, or run
`devstack apply` before tests that only need an ids file and a manifest. If a matching supervisor is
already live, `apply` reuses it instead of starting a second stack.

## How live ids reach a test

The committed `src/generated` tree is id-free — every on-chain value resolves at runtime through
`loadDeployment()`, which reads the build-injected `__DEVSTACK_DEPLOYMENT__` global (see
[Codegen](/devstack/codegen)). Under Vitest, Vite's `define` evaluates `__DEVSTACK_DEPLOYMENT__`
before `globalSetup` boots the stack, so the injected blob is `null` in the Node test environment. A
Node-only fallback bridges that:

1. Vitest's `globalSetup` boots the stack and publishes the booted stack's deployment-file path as
   `process.env.DEVSTACK_DEPLOYMENT_FILE`.
2. The generated `config-runtime.ts` reads that file the first time `loadDeployment()` is called,
   when `__DEVSTACK_DEPLOYMENT__` is `null` and `process.env.DEVSTACK_DEPLOYMENT_FILE` is set.

The net effect is that config reads inside a test pick up the **live** ids of the stack that
`globalSetup` booted, with no extra wiring. This fallback is Node-only; the browser build uses the
injected `__DEVSTACK_DEPLOYMENT__` value.
