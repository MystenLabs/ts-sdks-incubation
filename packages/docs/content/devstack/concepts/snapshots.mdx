---
title: Snapshots
description: docker commit + a host-fs copy. Cold starts in 5–15 s instead of minutes.
---

A snapshot bundles two things: the writable layers of every stateful container in the stack, and a
copy of the host-side `<stackDir>`. Together they're enough to skip the cold-seed pipeline on a
fresh checkout, a fresh CI runner, or after a `stack drop`.

```sh
devstack snapshot save baseline             # capture
devstack stack drop main --yes --force      # nuke
devstack snapshot restore baseline          # ~1 s
devstack up                                  # ~5 s — every getStatus says ok
```

This page explains what's in the bundle and why each piece is there. For the full CLI shape see
[`devstack snapshot`](/devstack/cli#snapshot).

## What gets captured

For each container labeled with the stack, the orchestrator reads the
`devstack.snapshot.{commit,quiesce}` labels (set by
[`containerService.snapshot`](/devstack/plugins/sui#snapshot-meta) at run time) and acts on them:

| Container's snapshot meta              | Capture step                                       |
| --------------------------------------- | -------------------------------------------------- |
| `commit: true, quiesce: 'pause'`       | `docker pause` → `docker commit` → `docker unpause`. Used for sui localnet (RocksDB single-writer; cgroup pause is the safe fast quiesce). |
| `commit: true, quiesce: 'stop'`        | `docker stop` → `docker commit` → `docker start`. Used for walrus storage nodes (graceful flush of write batches).                          |
| `commit: false, quiesce: 'none'`       | Skip entirely. Used for stateless containers (seal key-server, walrus proxy).                                                                |

Each `docker commit` produces an image tagged
`devstack-snapshot/<sha-id>/<container>:seeded` containing the writable-layer diff over the base
image. This is layer-deduped against the base in the docker daemon's image store, so a typical
sui chain commit is ~50 MB on disk regardless of how many snapshots you have.

The host bundle (`<appDir>/.devstack/snapshots/<sha-id>/`) holds:

```
<sha-id>/
  snapshot.json     # { id, alias?, createdAt, platform, containers: [{ containerName, originalImage, seedImage, registryImage? }] }
  host/             # recursive copy of <stackDir>
    manifest.json
    ports.json
    .keys/...
    setup/...
    walrus/deploy/...
    wallet-token
aliases/<name> -> ../<sha-id>     # symlink
```

Aliases are convenience names; the source of truth is the content-addressed `<sha-id>`.

## Content addressing

`<sha-id>` is `stableHash` of: `{ appName, stack, platform, suiImage, accountNames, plugin
versions/inputs }`. So:

- Two stacks with identical inputs → identical IDs → cache hit by construction.
- Bumping any plugin's image tag, account list, or sui version → different ID. Old snapshot
  remains on disk but no longer matches the new graph.
- Cross-arch is a hard mismatch: `darwin/arm64` and `linux/amd64` end up with different IDs. CI
  (Linux x86_64) and dev (Mac ARM) cache independently.

`devstack snapshot hash` prints the current `<sha-id>` without doing anything else — that's the
right value to use as a CI cache key.

## Restore

`devstack snapshot restore <alias|id>`:

1. Refuses if any container labeled for the target stack is still running. (`stack down` first.)
2. For each container in `snapshot.json`:
   - Verify the seed image is in the local docker daemon. If missing **and** a `registryImage` is
     recorded (from `snapshot save --push`), `docker pull` it.
   - `docker tag <seedImage> <originalImage>` — overwrites the local tag pointing at the base
     image to point at the seeded image instead. The plugin's hardcoded `image:` reference still
     resolves; it just gets the seeded layer now.
3. Replace `<stackDir>` with the bundle's `host/` contents.
4. Done — the next `devstack up` walks the action graph; every `getStatus` returns ok because the
   chain state is in the layer and the registry is hydrated from the restored `manifest.json`.

The trick is in step 2: `image tag` is the seam. Plugin code never knows it's running from a
seeded image vs a freshly-built one.

## Push (CI / cross-host)

```sh
devstack snapshot save baseline --push ghcr.io/myorg/devstack-snapshots
```

For each committed seed image, also tag as `<registry>/<container>:<alias>` and `docker push`.
`snapshot.json` records the registry tag in each container's `registryImage`. On restore, if the
local seed image is missing, the orchestrator pulls from the recorded registry tag.

This is the canonical CI pattern:

```yaml
seed:
  steps:
    - run: pnpm devstack up
    - run: pnpm devstack snapshot save baseline --push ghcr.io/${{ github.repository_owner }}/devstack-snapshots

e2e:
  needs: seed
  strategy:
    matrix: { shard: [1, 2, 3] }
  steps:
    - run: pnpm devstack snapshot restore baseline   # pulls seed images from GHCR
    - run: pnpm test:e2e --shard ${{ matrix.shard }}/3
```

The host bundle (small — KBs to a few MB depending on what setup writes) goes through GHA cache;
the seed images (the bulk of the bytes) go through GHCR with native layer dedup.

## What snapshots do *not* capture

- **Snapshots are inside-the-stack only.** They don't capture the docker daemon's base images
  themselves (those are built on first run and cached forever). On a brand-new CI runner with no
  base images, you still pay one cold image-build on the seed job.
- **Snapshots aren't isolation primitives for tests.** Multiple tests against the same stack
  share its container-layer state; restoring between tests would mean per-test container
  recreation (~3-5 s each). For per-test isolation use the
  [AccountPool fixture](/devstack/adapters/playwright) and per-test object scoping instead. Snapshots
  are a cold-start cache, not a test-reset mechanism.
- **Snapshots are platform-specific.** Cross-arch restore is refused by default (`--force-arch`
  to override) because RocksDB binary format may differ across architectures.
