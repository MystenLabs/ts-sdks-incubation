---
title: State and Snapshots
description: Current state layout and the supported snapshot command surface.
---

Runtime state is stack-scoped:

```txt
.devstack/stacks/<stack>/
  manifest.json
  projection.v1.json
  events.ndjson
  commands.ndjson
  runtime/
  snapshots/
```

The CLI exposes snapshot commands:

```bash
devstack snapshot save
devstack snapshot save --label before-migration
devstack snapshot list
devstack snapshot restore <id-or-label>
devstack snapshot delete <id-or-label>
```

One artifact lives under `.devstack/stacks/<stack>/snapshots/<snapshotId>/` and uses this layout:

```txt
meta.json
state.json
host-tree.tar
containers/<plugin>/<role>.tar
contributions/<encoded-plugin>.json
integrity.json
```

Supported behavior:

- Save requests are sent to the live supervisor through the command channel.
- Restore resolves an id or label, then asks the live supervisor to restore that artifact.
- List reads snapshot metadata from the active stack root and tolerates corrupt entries by showing a
  fallback row.
- Delete asks the supervisor to remove the resolved artifact.

Important caveats:

- Do not rely on cross-stack restore. Snapshot metadata carries app, stack, network, and plugin
  identity slices; restore is expected to refuse identity drift before destructive changes.
- Product evidence for non-empty wallet, Seal, Walrus, Postgres, and DeepBook roundtrips is still
  incomplete. These docs describe the supported CLI and artifact contract, not a claim that every
  service has full restore proof.
- Snapshot docs should point at `orchestrators/snapshot` and `cli/snapshot-reader` source when
  inspecting behavior. Old engine and snapshot-smoke paths are not current.

Use `devstack wipe --yes` to remove active stack state. Use `devstack stack drop <name>` when you
only want to delete a named stack root.
