`devstack(...)` returns a `DevstackHandle`. Calling its `run()` /
`runMain()` / `launchEffect()` boots the supervisor, which manages
every Ref's lifecycle.

This page is the load-bearing model for plugin authors and for
anyone debugging why a Ref isn't acquiring in the order they
expected.

## Phases

Every Ref moves through:

```
pending → acquiring → ready | failed
```

The TUI renders this in real time. `acquiring` rows narrate
sub-phases via `setPhase(...)` calls inside the body —
`"building image"`, `"genesis"`, `"requesting funds"`. `ready` rows
surface the Ref-supplied `display(value)` projection (URL,
packageId, address). `failed` rows show the short error in the row
plus the full cause walk in the log tail.

## Scopes

The supervisor creates three nested scopes:

```
supervisorScope ── lives for the entire `runMain` lifetime
  │
  ├── infraCtx       — registries, engine, state-store, identity,
  │                    platform services. Built once, survives
  │                    per-Ref failures and full-stack restarts.
  │
  ├── childScope[A]  — Ref A. Per-Ref scope; closes on A's failure
  ├── childScope[B]  — or on a full restart. Siblings stay alive
  ├── childScope[C]  — when one Ref fails.
  ├── …
  │
  └── longLivedScope — `Docker.run`'s adoptable containers register
                       `docker rm -f` finalizers here so press-`r`
                       full-restart leaves them running and the next
                       cycle adopts them (stable chain id, stable
                       package id).
```

Per-Ref failure tears down only that Ref's child scope. Siblings keep
running. Press `r` and the failed Ref's body re-runs.

Ctrl-C tears down the supervisor scope, which cascades through every
child scope's finalizer in reverse acquisition order.

## Hot restart

The supervisor watches paths declared via every Ref's `provide(...,
{ watch })` or `tag(..., { watch })` plus `config.watch`. Watcher
events are debounced 250ms. When the trailing edge fires:

1. The watcher fiber logs which Ref owns the changed path — e.g.
   `file change at ./move/hello/sources/foo.move (owned by
   packages.hello) — restarting`.
2. The current cycle's supervisor scope tears down (closing every
   `childScope`).
3. The launch loop returns from `runOnce` and re-enters with a new
   cycle number.
4. The cycle starts over with the same `infraCtx` (memoized) and
   fresh `childScope`s per Ref.

Long-lived docker containers registered on `longLivedScope` survive
the cycle teardown; the next cycle's `Docker.run` adopts them if
they're still healthy. Chain id stays stable, `publishMove` hits its
state-store cache, packageIds don't move.

## Hand-rolled run

Three entry points sit at different levels of abstraction:

- **`devstack(...).run()`** — Promise-returning. Resolves on clean
  shutdown. Use from a CLI entrypoint or a test fixture.
- **`devstack(...).runMain()`** — Same but uses
  `@effect/platform-node`'s `runMain` so SIGINT propagates to scope
  finalizers correctly. Best for production CLI use (the `devstack`
  binary uses this).
- **`devstack(...).launchEffect()`** — Raw launch Effect; lets a
  caller `yield*` it inside an outer NodeRuntime so SIGINT
  propagation reaches the launch loop's finalizers without nesting
  runtimes.
- **`devstack(...).layer`** — The composed `Layer.Layer` for
  Effect-native consumers that want to build their own runtime.

For test fixtures, the `vitest` and `playwright` subpaths wrap these
in fixture/helper shapes so your test code stays declarative — see
[vitest](../features/testing-vitest) and
[playwright](../features/testing-playwright).

## Multi-stack isolation

Every container, every state file, and every manifest path is keyed
on the `<app, stack, network>` triple. Two stacks on the same host
get separate containers, separate state, separate manifests — no
collision. The `DEVSTACK_STACK` env var overrides the stack name
per invocation; the network comes from the resolved `Sui(...)` Ref.
