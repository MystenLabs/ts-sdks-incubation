Symptoms grouped by where in the pipeline they surface. Each entry
is what you'd see, what's almost always going wrong, and how to
verify + recover.

## Docker not running / not reachable

**Symptom**: `Cannot connect to the Docker daemon at unix:///var/run/docker.sock`
or `error during connect: ... is the docker daemon running?` from any
`devstack` command that needs containers (`up`, `apply`, `stack
drop`).

**Cause**: Docker Desktop / Colima / Orbstack isn't started, or your
shell isn't pointed at the right socket.

**Fix**:

```bash
# macOS Docker Desktop: launch the app, then verify
docker info        # should print server info, not an error

# Colima
colima start
```

Verify with `docker ps` returning (an empty table is fine).

## Port collision on `devstack apply`

**Symptom**: `Bind for 0.0.0.0:9376 failed: port is already
allocated` (or any other port the sui plugin / wallet-server / vite
asked for).

**Cause** — three shapes:

1. **Another stack of the same app holds the port.** The per-stack
   port allocator avoids this — but if you've manually started a
   container with `docker run -p 9376:9000 ...` it bypasses the
   allocator.
2. **A non-devstack process holds the port.** The sui plugin's
   default `rpcPort: 9000` collides with anything else on 9000.
3. **A previous run's container survived a `docker rm -f` race.**

**Fix**:

```bash
lsof -i :9376                                # who's holding it
docker ps -a | grep <port-or-app-name>       # is it a stale container
pnpm devstack stack drop <stack-name> --yes --force   # nuke + retry
```

The per-stack port allocator picks a free port automatically when
the preferred one is taken — so a second stack of the same app
("test" while "main" runs) works without intervention as long as
you don't pin manually.

## Faucet 500 on cold first run

**Symptom**: `sui.accounts` fails on the first cycle of a fresh
sui container with `faucet http://127.0.0.1:9765/v2/gas → 500:
{"status":{"Failure":{"Internal":"Failed to execute transaction
after 2 retries"}}}`.

**Cause**: cold-genesis race — the faucet HTTP endpoint is up
before the validator is ready to execute coin txns. `keys.ts:64`
already retries with exponential backoff + jitter and absorbs the
common case; this only surfaces when the localnet container is
unusually slow on a constrained host.

**Fix**: wait + rerun.

```bash
pnpm devstack apply       # a few seconds later, the validator's caught up
```

If it persists across multiple retries, the sui-localnet container
itself is degraded — `docker logs <app>-<stack>-sui` for clues, then
`stack drop` + `apply` again.

## `mysten-dapp-kit-connect-button` never appears in e2e

**Symptom**: Playwright e2e fails with
`locator.click: Test timeout exceeded. waiting for locator
('mysten-dapp-kit-connect-button')`. The browser loaded the page
but no button rendered.

**Cause**: the React app crashed during initial mount. Common
shapes:

- A Node-only module (e.g. `node:child_process`) leaked into the
  browser bundle via a deep-import chain. Vite externalizes it
  and the page crashes with `Module "node:..." has been
  externalized for browser compatibility`.
- The dev-wallet adapter failed to register because `manifest
  .registry.services` is missing the `wallet-server` entry (cold
  first-run race).
- A bundle import error (typo, broken peer-dep version).

**Verify**:

```bash
# Open the page directly and watch for browser-console errors
pnpm devstack apply           # bring stack up
open http://localhost:5174/   # macOS; Linux: xdg-open ...
# DevTools → Console: any red errors are the cause
```

**Fix**: rebuild devstack (`cd packages/devstack && pnpm build`) if
you've touched plugin source, then restart the dev server.

## Walrus storage nodes don't become healthy

**Symptom**: `walrus.node-{0..3}` actions fail with
`waitForHealthy: '<app>-<stack>-walrus-node-N' did not become
healthy within 300000ms` (5 min × 4 nodes = ~20 min cold-up).

**Cause**: known walrus 1.48.0 bug — TLS server task panics in
`axum-server-0.8.0/src/tls_rustls/mod.rs:204:14` shortly after
binding REST API. See `notes/friction.md`.

**Fix**: no upstream fix in flight. Walrus-using flows that don't
need storage nodes (KeyServer registration, read-only queries,
deploy outputs) work fine. Blob upload (`private-content`'s
upload spec) is the only blocked path.

```bash
# Verify the panic
docker logs <app>-<stack>-walrus-node-0 | grep tls_rustls
```

## Snapshot restore mismatch

**Symptom**: `devstack snapshot restore <alias>` fails with
`snapshot id <sha> not found` or
`platform mismatch: snapshot is linux/amd64, host is darwin/arm64`.

**Cause** — three shapes:

1. **Alias doesn't exist.** Typo, or the snapshot was saved against
   a different stack (`--stack` flag mismatch).
2. **Cross-arch restore.** Snapshots are platform-tagged
   (`darwin/arm64` ≠ `linux/amd64`) because container writable layers
   include native binaries that don't roundtrip across arches. Use
   `--force-arch` to override (RocksDB binary format may corrupt;
   you've been warned).
3. **Snapshot dir wiped.** `<appDir>/.devstack/snapshots/` is
   gitignored; cleaning the directory loses snapshots.

**Fix**:

```bash
pnpm devstack snapshot list           # find the right alias / id
pnpm devstack snapshot list --json    # for scripted lookup
```

To rebuild a snapshot after a clean checkout: `devstack apply`
(cold), then `devstack snapshot save <alias>`.
