# Versioning + Compatibility-Shim Audit

**Scope.** `packages/devstack/src/**` and `packages/dev-wallet/src/**`. Read-only sweep for fossil
references to pre-release iteration vocabulary: `v3` / `v4` / `v5` tokens; Move-lock-unrelated
`Phase A/B/C/...` and `Phase 1/2/.../9` markers; `legacy`, `deprecated`, `migrate`,
`backwards-compat` phrases; cache-key version literals (`publishMove/v2`, `walrus/deploy-output/v3`,
etc.); schema version literals (`ManifestV5.version: Schema.Literal(5)`); and "fallback for old
shape" code branches that no longer have an "old" to fall back to.

**Important context.** devstack has never been released. Every `v<N>` token, "legacy" comment,
"migrate from" hint, and "pre-Phase-X" qualifier in the source tree is therefore — by definition —
**fossil noise from internal iteration plans**, not real backwards compatibility. The only
exceptions are:

1. **Upstream API version references** (`@mysten/deepbook-v3` package name; `/v1/accounts`,
   `/v2/gas`, `/v1/blobs/...` HTTP paths defined by the **upstream** sui-faucet / walrus /
   wallet-server contracts; `Move.lock` `version = 3` / `version = 4` / `[pinned.<env>.<pkg>]`
   sections which are the **upstream sui-CLI** lockfile format; `traefik:v3.6` image tag).
2. **External SDK version pins** (none of the matches in this scope are these).

Everything else — `ManifestV5`, `publishMove/v2/...` keys, "legacy v3 fallback decoder", "v3 parity
port" doc-comments, "Phase 5.2 of api-simplification.md" markers, "Phase B's topological scheduler",
`Walrus` composite tag references — should go.

Almost all fossil hits are **comments and doc-strings**. The only _behavioural_ fossils — code that
encodes the historical version into a load-bearing identifier — are:

- `runtime/manifest-schema.ts:225` — `version: Schema.Literal(5)` (manifest schema version).
- `engine/snapshot.ts:88` — `META_VERSION = 4 as const` (snapshot meta schema version).
- `services/package/internal.ts:571,575` — `publishMove/v2/...` namespace and `keyOverride` lock.
- `state-store-keys.ts:48-222` — every cached-artifact key carries a `v<N>` segment; some of those
  N's were bumped during pre-release iteration, but there's no consumer for the old N anywhere
  (in-tree or out-of-tree), so the version segment in the key is structural overhead.
- `engine/snapshot.test.ts:216-244` — test specifically asserts that a `version: 3` `meta.json` is
  rejected; the entire test is fossil (it asserts a backwards-incompat we have no obligation to
  maintain).
- `runtime/read-stack-context.test.ts:128-163` and `playwright/web-server.test.ts:126-170` — both
  test files assert that a "v3-shape" manifest produces a `ManifestShapeError`. These tests describe
  a migration we never owe.

Top 5 worst offenders (by fossil-noise density):

1. **`runtime/manifest-schema.ts` + `runtime/read-stack-context.ts` +
   `runtime/read-stack-context.test.ts`** — the entire `ManifestV5` naming convention (file-level
   header, every JSDoc, three test `describe` blocks, two test-only "v3 shape" fixtures, the
   `version: Schema.Literal(5)` field, and the error-message string
   `"does not match the v5 schema"`) is shaped around the assumption that v3 and v4 manifests exist
   and need to be rejected. They do not exist.
2. **`engine/snapshot.ts` + `engine/snapshot.test.ts`** — `META_VERSION = 4 as const`, "v4
   (current)" / "v3-shaped files are not parseable" prose, and a dedicated
   `list() skips a meta.json with a legacy v3 version` test (which is fossil-against-fossil).
3. **`services/package/internal.ts:564-575`** — the only place in the codebase that uses
   `keyOverride` to "preserve the legacy v2 state-store key shape because out-of-tree consumers
   reference this exact string". No out-of-tree consumers exist.
4. **`cli/commands/{doctor,stack,wipe,snapshot,prune,manifest}.ts`** — every command file begins
   with a "V3 parity port" / "matches v3" / "matches the v3 runner" prose block. The v3 it's
   "parity-porting" is dead.
5. **`engine/snapshot.docker.test.ts:101-118` + `services/deepbook.test.ts:163,367,513`** — three
   docker integration tests grep for `publishMove/v2/...` cache keys verbatim. If the
   `publishMove/v2/...` key drops to a canonical `publishMove/<chainId>/<inputsHash>` shape (per
   `notes/integration-contract-redesign.md`), these tests need to update their grep targets.

LoC delta projection: **~600 lines of comment removal + ~150 lines of dead test code + ~50 lines of
schema simplification = ~800 LoC**. No public surface change beyond the manifest-shape error message
and (optionally) a state-store cache key prefix drop.

Risk: **none load-bearing**. Two near-load-bearing points called out under §5.

## 3. Specific recommendations

### 3.1 `ManifestV5` → `Manifest`; drop `version` field

`runtime/manifest-schema.ts` is the cleanest case. The schema literal `version: Schema.Literal(5)`
has no consumer that branches on the value (grep showed only `version: 5 as const` write sites plus
the schema definition itself). Two options:

(a) **Drop the field entirely.** The schema decoder already rejects shapes missing the required
top-level fields (`stack`, `services`, `packages`, `accounts`, `coins`, `app`); the absence of a
`version` field doesn't open up any ambiguity.

(b) **Reset to v1.** Keep the `version: Schema.Literal(1)` field as a future-migration
discriminator. Lower-risk if you ever want to evolve the schema.

I'd recommend **(b)** — it's two characters of difference from (a) and preserves the option to add
migration logic later without re-introducing the field through a refactor.

Cascade: rename `ManifestV5` → `Manifest` across:

- `runtime/manifest-schema.ts`

- `runtime/read-stack-context.ts`

### 3.4 (Optional, larger) Collapse all state-store-key `v<N>` segments

`engine/state-store-keys.ts` currently encodes `publishMove/v2`, `walrusDeployOutput/v3`,
`deepbookBalanceManager/v2`, and 8 other prefixes that all sit at v1. None of these N values were
ever released; each was bumped during internal iteration. Two paths:

(a) **Collapse to v1 everywhere.** Drop the `v3` from `walrus/deploy-output/v3`, drop the `v2` from
`publishMove/v2`, drop the `v2` from `deepbook/market-maker/balance-manager/v2`. All cached entries
become orphaned, which is fine (the next devstack-up cycle just regenerates them).

(b) **Drop the version segment entirely.** The key becomes `${namespace}/${chainId}/${inputsHash}`.
Simpler.

I'd lean **(b)** — the `v<N>` segment was inherited from the convention `<service>/<artifact>/v<N>`
documented at the top of `state-store-keys.ts`, but that convention was specifically there to
support iteration-during-development. Post-release it adds no value: a value-shape change either
makes the cache miss naturally (a new field is required → decode fails → cache invalidates) or needs
an explicit cache-invalidation step (a script that walks the state-store and removes keys), which
`v<N>`-bumping doesn't actually solve cleanly either.

LoC delta: ~120 lines across `state-store-keys.ts` + its test + 11 callsites + the snapshot/
deepbook docker tests that grep on the key shape.

## 5. Risk

**Load-bearing version references:** the audit found **zero** load-bearing fossils. All remaining
`v<N>` tokens in the codebase fall cleanly into one of three buckets: upstream API identifier
(legitimate), iteration narrative in a comment (fossil), or unused schema literal (fossil).

**Near-load-bearing call-outs:**

1. `state-store.ts:402-431` un-versioned-file migration: removing this branch will cause devstack to
   fail-fast on any state.json file that lacks a `version` wrapper. Such files never existed in any
   released form, but a dev who has been running off a feature branch from October 2025
   (pre-versioning) might trip on it. Migration: `rm .devstack/stacks/*/state.json` and re-publish.
   Acceptable.

2. `engine/snapshot.ts:88` `META_VERSION = 4 as const`: dropping `4` → `1` will cause `list()` to
   silently skip any existing on-disk snapshot (the decoder treats version mismatch as "skip this
   entry"). Operators with on-disk snapshots from before the change would need to re-take them.
   Acceptable for unreleased software.

3. `state-store-keys.ts` collapse (§3.4 option b): any cached on-disk entries become orphaned. The
   next `devstack up` regenerates them, but operators with long-lived `.devstack/state.json` files
   will see an apparent "first run" cost on the next cycle. Acceptable.

**Test-name labels:** the `Phase N P<N>.<M>` test descriptors that point at deleted plan files
provide no value but also do no harm. Sweep them lazily.
